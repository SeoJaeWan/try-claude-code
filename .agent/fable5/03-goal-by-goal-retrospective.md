## 목표 1 - "구조 문제를 .codex/web에 정리하고 보고해"

### 받은 목표

문제 제기는 다음 네 가지였다.

- `/[category]` 페이지 부재
- SEO/metadata 미비
- 폴더 구조 문제
- `useIsMobile` 분리

마지막 지시는 ".codex에 web 폴더 만들고 정리하고 보고해"였다.

### 해석

마지막 문장을 기준으로 구현이 아니라 분석과 문서화 명령으로 해석했다.

따라서 코드 수정은 하지 않았다.

### 접근 판단과 근거

문서 형식을 새로 만들지 않았다.

기존 `.codex/layout/*.md`의 형식을 따랐다.

컨벤션은 요구 문장이 아니라 기존 산출물에서 찾는다는 판단이었다.

### 실행

스크립트 없이 정적 분석만 수행했다.

| 도구 | 대상 | 얻은 것 |
| --- | --- | --- |
| `find`, `ls` | 원본 blog `src/app`, 현재 `apps/web/src` | 라우트 3단계와 2단계 격차 |
| `Read` | 원본 layout, `[category]`, sitemap, robots | metadata 계약, 제목 유틸, 카테고리 사전, canonical 근거 |
| `find` | `packages/ui/src/components` | camelCase + `index.tsx`, 인접 `hooks/` 컨벤션 |
| `wc -l` | 셸 파일들 | `DesktopShell` 684줄이라는 분해 대상 정량화 |

### 검증과 충분성 판단

문서 단계의 검증자는 사용자다.

따라서 채택하지 않은 대안과 이유까지 문서에 명시해 리뷰에서 걸러질 수 있게 했다.

### 잔류물

- `routes.md`
- `structure.md`

이 문서들이 이후 모든 작업의 스펙이 됐다.

## 목표 2 - "types를 루트 types/로 빼면 어떨까?"

### 해석

단순 위치 이동이 아니라 타입의 전역성에 대한 설계 의견으로 받았다.

### 접근 판단과 근거

동의하되 숨은 모순을 처리했다.

`session.ts`에는 런타임 함수도 있으므로 `types/`로 통째로 옮기면 "타입만 두는 폴더"라는 규칙이 깨진다.

따라서 다음 규칙을 추가했다.

- 타입은 `types/`
- 런타임은 소비처로

같은 논리를 `contentTypes.ts`에도 적용했다.

근거는 원본 blog의 `src/types/{file,content}.ts` 선례였다.

### 실행

문서 세 곳만 수정했다.

- Target Layout
- Rules
- Migration Order

### 검증

사용자 승인으로 방향이 확정됐다.

## 목표 3 - "이 방향으로 개선을 진행해보자"

### 해석

목표 1과 2의 문서 두 개가 그대로 스펙이 됐다.

### 작업 분해와 근거

작업은 다음 순서로 진행했다.

1. 기계적 rename
2. 창 폴더화
3. `DesktopShell` 분해
4. 라우트/SEO
5. 검증

순서의 근거는 다음과 같다.

- 앞 단계가 뒤 단계의 전제다.
- 각 단계 종료 시 typecheck 통과 상태를 유지할 수 있다.

### 코드 수정 방식과 근거

이동은 `git mv`를 사용했다.

로직 이동과 동작 변경을 섞지 않았다.

리팩토링과 기능 변경이 섞이면 회귀 원인이 이동인지 변경인지 구분할 수 없기 때문이다.

계획 외 설계 변경도 있었다.

`desktopShell/index.tsx`와 `shellBody.tsx`의 2층 구조를 만들었다.

근거는 `usePinItemMenu`가 `PinProvider` 컨텍스트를 읽는다는 소스 확인이었다.

### 사용한 도구

| 도구 | 왜 | 성과 |
| --- | --- | --- |
| `git mv` | 이력 보존 rename | 리뷰 시 rename으로 추적 가능 |
| `sed` 일괄 치환 | 손 편집 누락 위험 감소 | `../` import를 `@/*`로 통일 |
| `eslint --fix` | import 정렬은 기계가 정확 | 정렬 에러 자동 해소 |

### 검증과 충분성 판단

수행한 검증은 다음과 같다.

- typecheck
- lint
- test
- build
- prod 서버 구동
- `curl`로 실제 응답 검증

확인한 실제 응답 예시는 다음과 같다.

- `<title>NEU - Blog</title>`
- canonical
- 404
- sitemap/robots 200

브라우저 인터랙션 검증은 생략했다.

재배치 중심이라 동작 불변이라고 판단했지만, 이 검증 범위 판단은 이후 목표에서 한계가 드러났다.

### 잔류물

- 신규 라우트/SEO 파일
- 실제 구조와 동기화된 `structure.md`
- 완료 표기된 Migration Order

## 목표 4 - "드래그 끊김 + 배경 창 첫 드래그 무반응 + 카테고리 일원화"

### 해석

성격이 다른 세 문제로 분리했다.

- 감각 버그
- 원인 불명 상태 버그
- 설계 개선

사용자의 이벤트 전파 차단 가설은 검증 대상으로만 취급했다.

### 접근 판단과 근거

원인 불명 상태 버그는 코드 리딩만으로 확정할 수 없었다.

따라서 재현 환경 구축이 선행 투자로 정당했다.

프로젝트 오염을 피하기 위해 scratchpad에 `playwright-core`를 설치하고 캐시된 Chromium을 사용했다.

### 계측 루프

| 스크립트 | 왜 만들었나 | 밝혀낸 것 |
| --- | --- | --- |
| `drag-repro.mjs` | 신고 증상 재현 | 배경 창 드래그 실패, 이동량 불일치 |
| `stack-debug.mjs` | 테스트 좌표 확인 | 타이틀바가 `y=-3`에 있어 테스트 결함이 아님 |
| `scroll-check/repeat.mjs` | 비결정 증상의 재현율 측정 | `scrollTop=75`가 4/6 발생 |
| screenshot | 시각 확정 | 타이틀바가 창 밖으로 밀림 |
| `verify-fixes.mjs` | 수정 후 정량 회귀 | 스크롤 0/6, 이동량 픽셀 일치 |

### 코드 수정과 근거

- `overflow: hidden`을 `clip`으로 바꿨다.
- 비율 기반 이동을 픽셀 오프셋으로 바꿨다.
- rAF coalescing으로 중복 업데이트를 제거했다.
- `CATEGORY_CONFIG`를 단일 출처로 만들었다.
- 테스트 중 발견한 `in` 연산자의 프로토타입 체인 문제를 `Object.hasOwn`으로 고쳤다.

### 검증과 충분성 판단

정량 회귀와 전체 verify를 통과했다.

하지만 prod 빌드에서만 확인했다.

사용자 환경인 dev가 변수라는 것을 놓쳤다.

## 목표 5 - "아직도 드래그 안 되는데?"

### 해석

세 가능성을 모두 열어두었다.

- 내 수정이 틀렸다.
- 다른 원인이 있다.
- 환경 차이가 있다.

전파 차단 가설은 `grep stopPropagation`으로 빠르게 기각했다.

### 전환점

환경을 실험 변수로 승격했다.

| 스크립트/조치 | 왜 | 기각/확정된 가설 |
| --- | --- | --- |
| `drag-matrix.mjs` | 환경 차이 검증 | prod 전부 성공, dev 전부 실패 |
| `stale-check.mjs` | dev가 옛 빌드인지 확인 | 기각 |
| dev 서버 재시작 | HMR 오염 확인 | 기각 |
| `cancel-check.mjs` | `pointercancel` 확인 | 기각 |
| `remount-check.mjs` | 리마운트 확인 | 리마운트는 기각, 세션이 시작 직후 죽는 사실 확정 |
| 임시 소스 probe | 외부 관찰 한계 돌파 | `beginPointerSession → unmount cleanup → endSession` 확정 |

### 수정과 근거

cleanup effect를 제거했다.

근거는 다음과 같다.

- `pointerup`/`pointercancel`이 리스너를 정리한다.
- 언마운트 후 `setState`는 React 18+에서 무해하다.

이 근거는 코드 주석으로 고정했다.

### 검증과 충분성 판단

dev와 prod 양쪽에서 검증했다.

- dev에서 세션이 DOM 재정렬을 살아남음
- 매트릭스 재통과
- prod 회귀 없음
- UI 테스트 43개
- 전체 verify

충분성 기준이 "내 재현 환경"에서 "사용자가 실제로 쓰는 모든 실행 모드"로 바뀌었다.

### 잔류물

- 코드 주석
- dev/prod 양쪽 검증 교훈
- Playwright 구동법
- 좌표 검증 요령

## 다섯 목표를 관통한 판단 기준

| 작업 성격 | 검증자 | 움직이기 전 필요한 확신 |
| --- | --- | --- |
| 설계 문서 | 사용자 | 대안과 근거가 문서에 드러나는가 |
| 리팩토링 | 기계 + 산출물 실측 | 각 단계가 빌드 가능한가, 실제 응답이 맞는가 |
| 원인 불명 버그 | 재현과 계측 | 원인이 측정으로 확정됐는가 |

검증이 충분한지에 대한 판단도 틀릴 수 있다.

틀렸음이 확인되면 그 교훈을 다음 세션이 읽을 위치에 남긴다.

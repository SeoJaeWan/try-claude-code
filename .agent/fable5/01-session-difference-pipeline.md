# Fable 5 Original 01 - 세션에서 차이가 드러난 지점과 실제 파이프라인

## 출처

사용자가 대화 본문에 정리한 Fable 5 작업 방식 메모.
```
이번 세션 기준으로 그 차이가 드러난 지점은 세 곳입니다:

  1. 그럴듯한 가설을 측정으로 기각한 것 — 드래그 버그에서 "DOM 재정렬로 리스너 끊김", "리마운트",
  "pointercancel", "HMR 컨텍스트 불일치" 등 4개 가설이 전부 그럴듯했습니다. 각각을 싼 실험으로 기각하지
  않고 첫 가설에서 바로 수정했다면, 증상은 가려지고 원인(StrictMode의 effect 재실행)은 남았을 겁니다.
  2. 검증 스크립트 자체를 의심한 것 — 테스트 실패가 두 번은 "제 잡기 좌표가 다른 창에 덮인" 테스트
  결함이었습니다. elementsFromPoint로 스택을 찍어보기 전까지는 버그 재현인지 테스트 결함인지 구분할 수
  없었습니다.
  3. 부수 버그를 지나치지 않은 것 — 테스트를 쓰다가 isContentCategory("toString")이 true가 되는 프로토타입
  체인 버그를 발견해 Object.hasOwn으로 고쳤습니다.

  작업 할당 → 목표 달성까지의 실제 파이프라인

  0단계. 계약 고정 (코드보다 문서)

  "라우트/폴더 구조 개선해줘" → 바로 코드를 안 고치고 .codex/web/routes.md, structure.md부터 작성했습니다.
  원본 프로젝트(~/Desktop/dev/blog)와 현재를 비교한 표, 목표 구조, 채택하지 않은 대안과 그 이유(셸을
  layout에 올리는 원본 방식 배제)까지. 이 문서가 이후 모든 판단의 기준점이 됩니다 — 당신이 "types를 루트로
  빼자"고 했을 때도 코드가 아니라 문서를 먼저 고쳤죠.

  1단계. 정적 분석

  find/grep/Read로 현재 상태 파악. 이때 핵심은 컨벤션의 출처를 찾는 것입니다 — "ui 프로젝트처럼"이라는
  요구에서 packages/ui의 실제 파일 배치(camelCase 폴더 + index.tsx, 인접 hooks/, 그룹 types.ts)를 먼저
  확인하고 그걸 규칙으로 삼았습니다.

  2단계. 구현 — 단계별로, 각 단계가 빌드 가능한 상태로

  태스크 5개로 나눠서(rename → 폴더화 → 분해 → 라우트 → 검증) 진행했고, 도중에 쓴 보조 도구들:

  - git mv — 이력 보존 rename
  - sed 일괄 치환 스크립트 — lint 규칙(../ 금지)에 걸린 상대경로 import 9종을 @/*로 한 번에 교체
  - eslint --fix — import 정렬 autofix

  3단계. 기계 검증 (매 단계)

  typecheck → lint → test → build. 여기까지는 누구나 하는 것이고, 실제로 이번 세션의 버그들은 전부 이 층을
  통과하고도 존재했습니다. 그래서 4단계가 본질입니다.

  4단계. 실동작 검증 — 세션 중 작성한 계측 스크립트들

  scratchpad에 일회용 Playwright 스크립트 12개를 작성했습니다(캐시된 Chromium을 playwright-core로 직접
  구동). 커밋하지 않는 임시 계측 도구로, 각각 목적이 달랐습니다:

  ┌─────────────────────────┬───────────────────────────────┬─────────────────────────────────────────┐
  │        스크립트         │             목적              │                밝혀낸 것                │
  ├─────────────────────────┼───────────────────────────────┼─────────────────────────────────────────┤
  │ drag-repro.mjs          │ 신고된 증상 최초 재현         │ 배경 창 첫 드래그 무반응 재현           │
  ├─────────────────────────┼───────────────────────────────┼─────────────────────────────────────────┤
  │ stack-debug.mjs         │ 잡기 지점 요소 스택 확인      │ 타이틀바가 y=-3에 있음 (테스트 결함     │
  │                         │                                │ 아님을 확정)                           │
  ├─────────────────────────┼────────────────────────────────┼────────────────────────────────────────┤
  │ scroll-check/repeat.mjs │ 프레임 scrollTop 측정 + 6회    │ overflow:hidden 프레임이 4/6 확률로    │
  │                         │ 반복                           │ 75px 스크롤됨                          │
  ├─────────────────────────┼────────────────────────────────┼────────────────────────────────────────┤
  │ focus-trace.mjs         │ focusin/scroll 이벤트 추적     │ 비결정성 확인                          │
  ├─────────────────────────┼────────────────────────────────┼────────────────────────────────────────┤
  │ remount-check.mjs       │ DOM 마커 + MutationObserver    │ 리마운트 아님, data-dragging true→즉시 │
  │                         │                                │  제거                                  │
  ├─────────────────────────┼────────────────────────────────┼────────────────────────────────────────┤
  │ cancel-check.mjs        │ pointercancel 여부 + dev/prod  │ pointercancel 없음 → React 내부가 세션 │
  │                         │ 비교                           │  종료                                  │
  ├─────────────────────────┼────────────────────────────────┼────────────────────────────────────────┤
  │ drag-matrix.mjs         │ 잡기지점×타이밍×서버 매트릭스  │ prod는 정상, 사용자 dev만 실패         │
  ├─────────────────────────┼────────────────────────────────┼────────────────────────────────────────┤
  │ stale-check.mjs         │ dev가 옛 코드인지 판별         │ 새 코드임 → dev 전용 버그 확정         │
  ├─────────────────────────┼────────────────────────────────┼────────────────────────────────────────┤
  │ verify-fixes.mjs        │ 수정 후 회귀 검증 (이동량 픽셀 │ 3개 수정 모두 정량 통과                │
  │                         │  비교)                         │                                        │
  └─────────────────────────┴────────────────────────────────┴────────────────────────────────────────┘

  마지막 확정은 스크립트로 안 돼서 ui 소스에 임시 console.debug + 스택 로그를 심고 재빌드 →
  beginPointerSession → unmount cleanup → endSession 호출 체인을 잡은 뒤 로그를 걷어냈습니다.

  5단계. 잔류물 남기기

  결과 코드만 남기는 게 아니라 — 결정 이유는 .codex 문서에, 재발 방지 근거는 코드 주석에(cleanup을 왜
  지웠는지), 프로세스 교훈은 메모리에("dev(StrictMode)에서도 검증할 것") 각각 남겼습니다.

  ---
  요약하면: "재현 → 계측 → 가설 기각 → 원인 확정 → 최소 수정 → 정량 재검증" 루프를 원인이 확정될 때까지
  도는 것이고, 그 과정에서 필요한 계측 도구는 그때그때 만들어 씁니다. 참고로 scratchpad의 스크립트들은
  세션 종료 시 사라지는데, verify-fixes.mjs 같은 회귀 검증은 프로젝트 스크립트로 승격해둘 가치가 있습니다
  ---
```

## 이번 세션 기준으로 차이가 드러난 세 지점

### 1. 그럴듯한 가설을 측정으로 기각한 것

드래그 버그에서 다음 가설들은 모두 그럴듯했다.

- DOM 재정렬로 리스너가 끊긴다.
- 컴포넌트가 리마운트된다.
- `pointercancel`이 발생한다.
- HMR 또는 dev 컨텍스트가 꼬였다.

하지만 각 가설을 싼 실험으로 기각하지 않고 첫 가설에서 바로 수정했다면, 증상만 가려지고 실제 원인인 StrictMode의 effect 재실행은 남았을 것이다.

### 2. 검증 스크립트 자체를 의심한 것

테스트 실패 중 두 번은 실제 버그가 아니라 잡기 좌표가 다른 창에 덮인 테스트 결함이었다.

`elementsFromPoint`로 포인터 지점의 요소 스택을 찍기 전까지는 다음 둘을 구분할 수 없었다.

- 버그가 재현된 것
- 검증 스크립트가 잘못 관측한 것

따라서 실패한 테스트도 즉시 사실로 취급하지 않는다. 먼저 관측 장치가 올바른지 확인한다.

### 3. 부수 버그를 지나치지 않은 것

테스트를 쓰는 과정에서 `isContentCategory("toString")`이 `true`가 되는 프로토타입 체인 버그를 발견했다.

이는 `in` 연산자의 특성 때문이었고, `Object.hasOwn`으로 고쳤다.

핵심은 원래 목표의 주변에서 발견된 결함이라도, 같은 책임 경계 안에 있고 재발 위험이 명확하면 지나치지 않는다는 점이다.

## 작업 할당부터 목표 달성까지의 실제 파이프라인

### 0단계. 계약 고정 - 코드보다 문서

요청은 "라우트/폴더 구조 개선해줘"였지만, 바로 코드를 고치지 않았다.

먼저 다음 문서를 작성했다.

- `.codex/web/routes.md`
- `.codex/web/structure.md`

문서에는 다음 내용이 포함됐다.

- 원본 프로젝트와 현재 프로젝트 비교표
- 목표 라우트/폴더 구조
- 채택하지 않은 대안
- 셸을 layout에 올리는 원본 방식을 배제한 이유

이 문서가 이후 모든 판단의 기준점이 됐다.

사용자가 "types를 루트로 빼자"고 했을 때도 코드가 아니라 문서를 먼저 고쳤다.

### 1단계. 정적 분석

`find`, `grep`, `Read`로 현재 상태를 파악했다.

핵심은 컨벤션의 출처를 찾는 것이었다.

"ui 프로젝트처럼"이라는 요구에서 실제 기준은 추측이 아니라 `packages/ui`의 파일 배치였다.

- camelCase 폴더
- `index.tsx`
- 인접 `hooks/`
- 그룹 `types.ts`

이 실제 배치를 규칙으로 삼았다.

### 2단계. 구현 - 단계별로, 각 단계가 빌드 가능한 상태로

작업은 다섯 단계로 나눴다.

1. rename
2. 폴더화
3. 분해
4. 라우트
5. 검증

도중에 쓴 보조 도구는 다음과 같다.

- `git mv`: 이력 보존 rename
- `sed` 일괄 치환 스크립트: lint 규칙에 걸린 상대경로 import 9종을 `@/*`로 교체
- `eslint --fix`: import 정렬 autofix

### 3단계. 기계 검증

매 단계마다 다음 검증을 수행했다.

- typecheck
- lint
- test
- build

하지만 이번 세션의 실제 버그들은 이 층을 통과하고도 존재했다.

따라서 기계 검증은 필요조건이지 충분조건이 아니다.

### 4단계. 실동작 검증 - 일회용 계측 스크립트

scratchpad에 일회용 Playwright 스크립트를 작성했다.

프로젝트를 오염시키지 않기 위해 캐시된 Chromium을 `playwright-core`로 직접 구동했다.

각 스크립트의 목적은 달랐다.

| 스크립트 | 목적 | 밝혀낸 것 |
| --- | --- | --- |
| `drag-repro.mjs` | 신고된 증상 최초 재현 | 배경 창 첫 드래그 무반응 재현 |
| `stack-debug.mjs` | 잡기 지점 요소 스택 확인 | 타이틀바가 `y=-3`에 있음. 테스트 결함이 아님을 확정 |
| `scroll-check/repeat.mjs` | 프레임 `scrollTop` 측정과 6회 반복 | `overflow:hidden` 프레임이 4/6 확률로 75px 스크롤됨 |
| `focus-trace.mjs` | `focusin`/`scroll` 이벤트 추적 | 비결정성 확인 |
| `remount-check.mjs` | DOM 마커와 `MutationObserver` 확인 | 리마운트가 아니라 `data-dragging`이 즉시 제거됨 |
| `cancel-check.mjs` | `pointercancel` 여부와 dev/prod 비교 | `pointercancel` 없음. React 내부가 세션을 종료 |
| `drag-matrix.mjs` | 잡기 지점, 타이밍, 서버 모드 매트릭스 | prod 정상, 사용자 dev만 실패 |
| `stale-check.mjs` | dev가 옛 코드인지 판별 | 새 코드임. dev 전용 버그 확정 |
| `verify-fixes.mjs` | 수정 후 회귀 검증 | 3개 수정 모두 이동량 픽셀 비교로 정량 통과 |

마지막 원인 확정은 외부 스크립트만으로 부족했다.

그래서 UI 소스에 임시 `console.debug`와 스택 로그를 심고 재빌드했다.

그 결과 다음 호출 체인을 확인했다.

```text
beginPointerSession
→ unmount cleanup
→ endSession
```

원인을 확정한 뒤 임시 로그는 제거했다.

### 5단계. 잔류물 남기기

결과 코드만 남기지 않았다.

잔류물은 성격에 따라 다른 위치에 남겼다.

- 결정 이유: `.codex` 문서
- 재발 방지 근거: 코드 주석
- 프로세스 교훈: 메모리

예를 들어 cleanup을 왜 지웠는지는 코드 주석에 남겼다.

dev StrictMode에서도 검증해야 한다는 교훈은 다음 작업의 프로세스 기준으로 남겼다.

## 요약

Fable 5의 핵심 루프는 다음과 같다.

```text
재현
→ 계측
→ 가설 기각
→ 원인 확정
→ 최소 수정
→ 정량 재검증
```

이 루프를 원인이 확정될 때까지 반복한다.

필요한 계측 도구는 그때그때 만든다.

scratchpad의 스크립트는 세션 종료 시 사라져도 되지만, `verify-fixes.mjs`처럼 회귀 검증 가치가 있는 것은 프로젝트 스크립트로 승격할 가치가 있다.

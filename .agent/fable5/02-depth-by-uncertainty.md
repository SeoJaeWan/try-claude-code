  반영했습니다.

## 기본 명제

루프 자체는 항상 같다.

```text
해석
→ 계획
→ 실행
→ 검증
→ 잔류물
```

하지만 각 단계의 깊이는 다음 값에 비례해서 조절한다.

```text
불확실성 × 틀렸을 때의 비용
```

오타 수정에 계측 스크립트 12개를 쓰지 않는다.

반대로 원인 불명 버그에 typecheck만 돌리고 끝내지도 않는다.

## 목표 1 - "구조 문제를 .codex/web에 정리하고 보고해"

### 받아들인 방식

요청 안에는 네 가지 문제 제기가 있었다.

- 카테고리 페이지 부재
- SEO/metadata 미비
- 폴더 구조 문제
- `useIsMobile` 분리

하지만 마지막 문장인 "정리하고 보고해"를 기준으로 구현 명령이 아니라 분석과 문서화 명령으로 해석했다.

따라서 이 단계에서는 코드를 수정하지 않았다.

### 판단과 근거

문서 형식을 새로 만들지 않았다.

레포에 이미 `.codex/layout/*.md`, `.codex/notion/*.md`가 있었고, 거기에 일관된 형식이 있었다.

- Purpose
- Source Evidence
- Scope
- 모델

컨벤션은 요구사항 문장이 아니라 기존 산출물에서 찾는다는 원칙을 적용했다.

### 실행

스크립트는 필요 없었다.

정적 읽기로 충분했다.

분석한 대상은 세 가지였다.

- 원본 blog의 라우트와 metadata 코드
- 현재 `apps/web`
- 목표 컨벤션의 기준이 되는 `packages/ui`

### 검증과 한계 인식

문서 단계의 검증자는 기계가 아니라 사용자다.

따라서 채택하지 않은 대안과 그 이유까지 명시했다.

판단이 틀렸다면 이 시점에 사용자가 걸러낼 수 있게 하기 위함이다.

## 목표 2 - "types.ts를 루트 types/로 빼면 어떨까?"

### 받아들인 방식

단순한 위치 이동 제안이 아니라 타입의 전역성에 대한 설계 의견으로 받았다.

### 판단과 근거

제안에 동의하되 숨은 모순을 먼저 드러냈다.

`session.ts`에는 타입뿐 아니라 런타임 함수인 `folderSessionId`도 있었다.

따라서 파일을 통째로 `types/`로 옮기면 "타입만 두는 폴더"라는 취지가 깨진다.

결론은 다음과 같았다.

- 타입은 `types/`
- 런타임 값과 함수는 소비처로

같은 논리를 `contentTypes.ts`에도 확장했다.

근거는 원본 blog가 이미 `src/types/{file,content}.ts` 컨벤션을 사용했다는 사실이었다.

### 실행과 검증

코드가 아니라 문서 세 곳만 수정했다.

- Target Layout
- Rules
- Migration Order

검증은 사용자 승인으로 이루어졌다.

## 목표 3 - "이 방향으로 개선을 진행해보자"

### 받아들인 방식

목표 1과 2에서 고정된 문서가 그대로 스펙이 됐다.

해석의 여지가 거의 없는 상태로 구현에 들어갔다.

### 작업 분해와 근거

작업은 다섯 개로 나눴다.

1. 기계적 rename
2. 창 폴더화
3. `DesktopShell` 분해
4. 라우트/SEO
5. 검증

순서의 근거는 두 가지였다.

- 앞 단계가 뒤 단계의 전제다.
- 각 단계 종료 시점마다 typecheck가 통과하는 상태를 유지할 수 있다.

### 코드 수정 방식과 근거

이동은 `git mv`로 했다.

새 로직을 섞지 않고 기존 코드를 최대한 그대로 옮겼다.

리팩토링과 기능 변경을 섞으면 버그 원인을 추적할 수 없기 때문이다.

계획에 없던 설계 변경도 있었다.

`desktopShell/index.tsx`와 `shellBody.tsx`의 2층 구조를 만든 것이다.

이는 추측이 아니라 소스 확인에서 나온 결정이었다.

`usePinItemMenu`가 `useOptionalPins()`로 `PinProvider` 컨텍스트를 읽고 있었기 때문에 메뉴 훅은 Provider 안쪽에서 호출되어야 했다.

### 사용한 도구

- `git mv`: 이력 보존
- `sed`: `../` import 9종을 `@/*`로 교체
- `eslint --fix`: import 정렬

### 검증과 충분성 판단

다음 검증을 수행했다.

- typecheck
- lint
- test
- build
- prod 서버 구동
- `curl`로 실제 HTML의 `title`, canonical, robots/sitemap 상태코드 확인

라우트/metadata 작업의 산출물은 빌드 통과가 아니라 크롤러가 받는 실제 응답이므로, 그 층까지 확인했다.

다만 브라우저 인터랙션 검증은 생략했다.

파일 재배치 중심이라 동작 변화가 없다고 판단했기 때문이다.

이 판단은 목표 4와 5에서 절반만 맞았던 것으로 드러났다.

## 목표 4 - "드래그 끊김 + 배경 창 첫 드래그 무반응 + 카테고리 관리 일원화"

### 받아들인 방식

성격이 다른 세 문제로 분리했다.

- 성능/감각 버그
- 원인 불명 기능 버그
- 설계 개선

사용자가 제시한 "이벤트 전파 차단 아닐까"라는 가설은 검증 대상으로만 받았다.

### 판단

코드 리딩만으로는 배경 창 첫 드래그 무반응 원인을 확정할 수 없었다.

상태 의존적 증상은 재현 없이 원인 단정이 불가능하다.

따라서 Playwright 기반 재현 환경을 먼저 만들었다.

프로젝트를 오염시키지 않기 위해 scratchpad에 `playwright-core`를 설치하고 캐시된 Chromium을 사용했다.

### 계측 루프

실제 흐름은 다음과 같았다.

```text
drag-repro
→ stack-debug
→ scroll-check/repeat
→ focus-trace
→ screenshot
→ verify-fixes
```

중요한 점은 테스트 실패를 곧바로 버그 재현으로 보지 않았다는 것이다.

먼저 잡기 좌표가 올바른지, 어떤 요소가 포인터 지점 위에 있는지 확인했다.

### 코드 수정과 근거

- `overflow: hidden`을 `clip`으로 변경했다.
- 드래그 비율 계산을 픽셀 오프셋 계산으로 변경했다.
- rAF coalescing으로 프레임당 중복 `setState`를 줄였다.
- `CATEGORY_CONFIG`를 단일 출처로 만들었다.

### 검증과 오류

`verify-fixes.mjs`로 스크롤 0/6과 이동량 픽셀 일치를 확인했다.

하지만 prod 빌드에서만 검증했다.

사용자 환경인 dev 모드를 변수로 넣지 못했고, 이 검증 충분성 판단은 틀렸다.

## 목표 5 - "아직도 드래그 안 되는데?"

### 받아들인 방식

세 가능성을 모두 열어두었다.

- 내 수정이 잘못됐다.
- 다른 원인이 더 있다.
- 사용자 환경이 다르다.

사용자의 전파 차단 가설은 `grep stopPropagation`으로 빠르게 확인했고, 닫기 버튼뿐이라 기각했다.

### 결정적 판단

환경을 변수로 넣은 매트릭스가 전환점이었다.

`drag-matrix.mjs`로 다음을 교차 실행했다.

- 잡기 지점
- 제스처 타이밍
- prod/dev 서버

결과는 prod 전부 성공, dev 전부 실패였다.

문제가 코드 차이가 아니라 실행 모드 차이로 좁혀졌다.

이후 다음 가설을 순서대로 기각했다.

- dev가 옛 코드인가: 아님
- HMR 오염인가: fresh dev에서도 실패
- `pointercancel`인가: 이벤트 없음
- 리마운트인가: 아님

단, `data-dragging`이 시작 직후 제거된다는 사실을 확보했다.

마지막에는 소스에 임시 `console.debug`와 스택 로그를 심어 호출 체인을 확정했다.

### 수정과 근거

cleanup effect를 제거했다.

지우는 수정이라 근거를 더 신중하게 남겼다.

- `window`의 `pointerup`/`pointercancel`이 리스너를 정리한다.
- 언마운트 후 `setState`는 React 18+에서 무해하다.

이 논증은 코드 주석으로 남겼다.

### 검증

이번에는 dev와 prod 양쪽에서 검증했다.

- dev에서 `data-dragging`이 DOM 재정렬을 살아남는지 확인
- 매트릭스 재통과
- prod 회귀 없음
- UI 테스트 43개
- 전체 verify

목표 4의 실패를 프로세스 교훈으로 남겼다.

## 관통 원리

각 목표에서 형태는 달랐지만 판단 기준은 하나였다.

```text
지금 내가 아는 것은 사실인가, 추측인가?
추측이라면 가장 싸게 확정하는 방법은 무엇인가?
```

문서 작업은 사람의 리뷰가 검증이다.

리팩토링은 기계 검증과 산출물 실측이면 충분할 수 있다.

원인 불명 버그는 재현과 계측 없이는 고치지 않는다.

검증의 충분성 판단조차 틀릴 수 있으므로, 틀렸음이 드러나면 그 교훈 자체를 잔류물로 남긴다.

# Fable 5 Original 04 - 목표 접수부터 완료 선언까지의 운영 모델

## 출처

첨부 원문: `085b55e7-57b7-405a-83bd-040dba45ee3e/pasted-text.txt`
```
목표를 받는 순간부터 끝났다고 선언하는 순간까지를 생략 없이
  풀어보겠습니다.

  ---
  1. 목표 접수 — 문장을 그대로 믿지 않고 세 가지를 먼저 정한다

  목표가 들어오면 코드를 열기 전에 세 가지를 정합니다.

  첫째, 이 발화의 종류. 같은 문장이라도 ① 실행 명령("진행해보자"), ② 설계 질문("~하면 어떨까?"), ③ 문제
  제보("드래그가 안 돼")는 완전히 다른 응답을 요구합니다. ①은 끝까지 실행하고, ②는 코드가 아니라
  의견+문서로 답하고, ③은 수정이 아니라 진단이 1차 산출물입니다. 이번 세션에서 "정리하고 보고해"를 구현
  명령으로 읽었다면 스펙 합의 없이 코드부터 갈아엎었을 것이고, 당신이 준 "전파 차단 아닐까"라는 가설을
  명령으로 읽었다면 존재하지 않는 원인을 "수정"했을 겁니다.

  둘째, 명시된 요구와 암묵적 요구의 분리. "카테고리 추가 시 수정할 곳이 많다"는 명시적 요구지만, 그 뒤에는
  "앞으로 카테고리가 늘어난다"는 암묵적 전제가 있습니다. 그래서 해법도 "지금 3개를 정리"가 아니라 "N번째
  추가 비용을 1로 만드는 구조"여야 했습니다.

  셋째, 완료 조건의 정의. 시작 전에 "무엇이 확인되면 끝인가"를 스스로 정합니다. SEO 작업이면 "빌드 통과"가
  아니라 "크롤러가 받을 실제 HTML의 title/canonical이 맞다"까지, 드래그 버그면 "코드가 그럴듯해졌다"가
  아니라 "재현되던 조작이 정량적으로(픽셀 단위) 성공한다"까지. 완료 조건을 느슨하게 잡으면 나중에 검증도
  느슨해집니다.

  ---
  2. 애매함 처리 — 모든 애매함이 질문거리는 아니다

  애매한 지점이 나오면 세 부류로 나눠서 각각 다르게 처리합니다.

  (A) 사실 확인으로 해소되는 애매함 → 스스로 해소한다. "ui 프로젝트처럼 해줘"에서 'ui 프로젝트처럼'이
  뭔지는 물어볼 일이 아니라 packages/ui의 실제 파일 배치를 읽으면 됩니다. "메뉴 훅을 어디 둬야 하나"도
  usePinItemMenu 소스를 읽어 PinProvider 의존을 확인하면 답이 나옵니다. 코드·문서·git 이력에서 확인 가능한
  것을 사용자에게 묻는 건 시간 낭비입니다.

  (B) 합리적 기본값이 있는 애매함 → 결정하고, 결정했음을 드러낸다. 배포 도메인이 미정이었을 때 원본이
  seojaewan.com이므로 그걸 기본값으로 하되 env로 오버라이드 가능하게 했고, 보고에 명시했습니다.
  desktopShell을 2층으로 나눈 것도 문서에 없던 결정이지만 제약(컨텍스트 의존)이 근거였으므로 진행하고
  문서에 역반영했습니다. 핵심은 몰래 결정하지 않는 것 — 결정과 근거를 보고와 문서에 남겨 당신이 뒤집을 수
  있게 합니다.

  (C) 사용자만 답할 수 있는 애매함 → 멈추고 묻거나, 보고하고 기다린다. 되돌리기 어렵거나 취향/전략이
  갈리는 것들입니다. 이번 세션의 예: page.test.tsx가 반복 삭제됐을 때. 처음엔 사고로 판단해 복원했지만(그
  시점의 증거: 커밋 메시지에 삭제 의도가 없음), 세 번째 삭제에서 증거의 무게가 "의도"로 기울자 행동을 
  멈추고 판단 근거와 함께 보고했습니다. 제 복원이 맞는지 당신의 의도가 맞는지는 저에게 결정권이 없는
  문제니까요. 또 하나: 원본의 google/naver verification 코드는 Search Console 속성에 묶인 값이라 제가
  넣을지 말지 결정할 사안이 아니어서, 빼고 이유를 보고했습니다.

  정리하면 — 애매함의 해소 주체를 먼저 판별합니다. 사실이면 내가, 기본값이면 내가(단 투명하게), 권한
  밖이면 당신이.

  ---
  3. 현재 상태 파악 — 코드보다 "기준"을 먼저 찾는다

  구현 전 정적 분석에서 찾는 것은 세 가지입니다.

  1. 기준(무엇과 비교하는가) — 이 프로젝트는 원본 blog와 seojaewan.com이 UX/기능 기준이므로, 라우트 작업
  전에 원본의 layout/sitemap/robots/카테고리 metadata를 전부 읽었습니다.
  2. 컨벤션(어떤 모양이어야 하는가) — lint 설정, 기존 파일들의 실제 배치, import 스타일. lint가 알려주기
  전에 먼저 맞추면 재작업이 줄어듭니다(이번엔 ../ 금지 규칙을 늦게 발견해 sed로 일괄 교정 — 이것도 다음엔
  eslint config를 먼저 읽는 게 낫다는 학습).
  3. 제약(무엇이 설계를 강제하는가) — sync 스크립트가 tsx로 실행되어 @/ alias를 못 쓴다는 제약이 "config
  파일은 alias-free"라는 설계를 결정했습니다. 제약을 늦게 발견하면 설계를 다시 해야 하므로,
  소비자(스크립트, CI 워크플로)까지 먼저 훑습니다.

  ---
  4. 계획 — 분해의 단위는 "되돌아갈 수 있는 지점"

  작업 분해 기준은 두 가지입니다: 각 단계가 끝날 때 시스템이 검증 가능한 상태인가(typecheck가 도는가),
  그리고 앞 단계가 뒤 단계의 전제인가(의존 순서). 그래서 리팩토링은 "기계적 rename → 폴더화 → 로직 분해 →
  라우트"였습니다 — 어느 단계에서 문제가 나도 그 단계만 의심하면 됩니다.

  규모가 크거나 판단이 개입되는 작업은 계획을 문서로 먼저 고정합니다(.codex/web). 이유는 두 가지: 작업 중
  판단이 흔들리지 않고, 당신이 코드가 아니라 계획 단계에서 개입할 수 있습니다(실제로 types 위치가 그렇게
  교정됐습니다). 반대로 자명한 소규모 작업은 문서 없이 바로 갑니다 — 문서화 자체도 비용이므로.

  ---
  5. 실행 — 코드를 고칠 때의 규칙들

  - 원인 층위에서 최소로. 증상을 덮는 코드(스크롤 되돌리기, 세션 재시작 로직)를 추가하지 않고 원인을
  제거합니다(overflow: clip, cleanup 삭제). 특히 "지우는 수정"은 지워도 안전하다는 논증을 완성한 뒤에만
  합니다 — cleanup 삭제 때 "pointerup은 항상 발생한다 + 언마운트 후 setState는 무해하다"는 두 근거를
  확보하고 지웠습니다.
  - 리팩토링과 동작 변경을 절대 섞지 않는다. 파일 이동 단계에서는 로직을 한 글자도 안 바꿉니다. 섞이면
  회귀의 원인이 이동인지 변경인지 구분할 수 없게 됩니다.
  - 주석은 "왜"만. 코드가 말할 수 없는 것 — 왜 cleanup이 없는지, 왜 비율이 아니라 픽셀인지 — 만 남깁니다.
  미래의 누군가가 "정상화"라며 되돌리는 것을 막는 게 주석의 역할입니다.
  - 도구 선택 기준은 오류 확률. 9개 파일의 동일 패턴 치환은 손 편집(누락 위험)이 아니라 sed + 사후
  grep(잔여 0 확인), 정렬은 사람이 아니라 eslint --fix, 이동은 mv가 아니라 git mv(이력).

  ---
  6. 막혔을 때 — 가설-측정 루프의 실제 규칙

  예상과 다른 상황(버그, 이상 동작)을 만나면 모드가 바뀝니다. 이때의 규칙:

  규칙 1. 재현 없이는 수정 없다. 재현이 안 되는 버그를 고치는 건 어둠 속 사격입니다. 재현 환경이 없으면
  만드는 것 자체가 첫 작업입니다(playwright-core + 캐시 Chromium — 레포 오염 없이).

  규칙 2. 가설은 복수로 세우고, 각 가설에 "판별 실험"을 붙인다. 좋은 실험의 조건은 결과가 가설을 갈라놓는
  것입니다. "리마운트라면 DOM 마커가 사라져야 한다", "pointercancel이라면 이 리스너가 울려야 한다" —
  울리지 않으면 그 가설은 죽습니다. 이번 세션에서 가설 4개가 이렇게 죽었고, 죽을 때마다 남은 공간이
  좁아졌습니다.

  규칙 3. 실험은 싼 것부터. grep stopPropagation(1초) → 스크립트 계측(분 단위) → 소스에 프로브 심고
  재빌드(가장 비쌈) 순서로 올라갑니다. 마지막 수단(소스 계측)은 외부 관찰로 판별이 안 될 때만 쓰고, 확정
  즉시 걷어냅니다.

  규칙 4. 측정 도구 자체를 의심한다. "테스트 실패 = 버그 재현"이 아닙니다. 이번에 두 번, 실패의 원인이 제
  테스트 좌표(다른 창에 덮임, boundingBox 이상값)였습니다. 이상한 결과가 나오면 결론 내리기 전에 관측
  장치를 먼저 검증합니다(elementsFromPoint로 스택 확인).

  규칙 5. 비결정적 증상은 재현율을 측정한다. "가끔 된다"는 보고는 쓸모가 없으므로 6회 반복으로 4/6이라는
  숫자를 만들었고, 수정 후 0/6으로 닫았습니다. 숫자가 있어야 "고쳐졌다"를 말할 수 있습니다.

  규칙 6. 규명은 수정의 정당성에 필요한 만큼만. 브라우저가 왜 스크롤시키는지의 내부 메커니즘은 끝까지 안
  쫓았습니다 — clip이 메커니즘과 무관하게 문제를 차단하므로. 반대로 "누가 세션을 죽이는가"는 스택까지
  쫓았습니다 — 그걸 모르면 무엇을 지워야 할지 모르므로. 호기심이 아니라 수정 근거가 규명의 깊이를
  정합니다.

  ---
  7. 검증 — 층위와, "충분함"의 판단

  검증은 4층입니다: typecheck/lint(기계적 오류) → test/build(계약) → 실동작(서버 띄우고 실제 응답/조작
  확인) → 사용자 환경 재현(dev/prod, 실제 제스처, 겹친 창 좌표). 이번 세션의 교훈은 3층까지 통과한 버그가
  존재했고, 4층에서 prod만 확인해서 dev 버그를 놓쳤다는 것입니다. 그래서 지금의 기준은: **검증 환경은
  "내가 재현한 환경"이 아니라 "사용자가 실행하는 모든 모드"**여야 하고, 이 교훈은 메모리에 저장해 다음
  세션에도 적용됩니다.

  "이 정도면 충분한가"의 판단 기준은 결국 틀렸을 때의 비용입니다. 문서는 리뷰로 충분하고, 재배치는 기계
  검증+실측으로, 인터랙션 버그는 정량 재현 검증까지. 그리고 검증이 불충분했음이 드러나면(목표 4→5), 그것을
  실패로 기록하고 기준 자체를 올립니다 — 검증 체계도 수정 대상입니다.

  ---
  8. 보고와 잔류물 — 끝났다고 말하는 방식

  보고는 결론부터("원인을 찾아 고쳤습니다"), 그다음 근거, 그다음 상세. 그리고 세 가지를 숨기지 않습니다:
  제가 내린 재량 결정(verification 코드 제외), 제가 틀렸던 것(prod만 검증), 제 권한 밖의 이상
  징후(page.test.tsx 반복 삭제).

  잔류물은 종류별로 "다시 필요해질 위치"에 남깁니다:
  - 결정의 이유 → .codex 문서 (다음 설계 때 읽힘)
  - 코드의 반직관적 형태에 대한 방어 → 코드 주석 (그 줄을 고치려는 사람이 읽음)
  - 프로세스 교훈 → 메모리 (다음 세션의 내가 읽음)
  - 일회용 계측 → scratchpad (남기지 않음 — 단, 회귀 가치가 있으면 승격 제안)

  ---
  한 문장으로

  "모든 명제를 '확인된 사실'과 '추측'으로 분류하고, 행동은 사실 위에서만, 추측은 가장 싼 실험으로 사실로 
  바꾸며, 해소 주체가 내가 아닌 애매함은 투명하게 위로 올린다" — 목표 접수부터 완료 선언까지 매 단계에서
  도는 것은 이 하나의 판별 루프입니다.
```

## 1. 목표 접수 - 문장을 그대로 믿지 않는다

목표가 들어오면 코드를 열기 전에 세 가지를 먼저 정한다.

### 첫째, 발화의 종류

같은 문장이라도 종류에 따라 응답 방식이 달라진다.

- 실행 명령: 끝까지 실행한다.
- 설계 질문: 코드가 아니라 의견과 문서로 답한다.
- 문제 제보: 수정이 아니라 진단이 1차 산출물이다.

"정리하고 보고해"를 구현 명령으로 읽었다면 스펙 합의 없이 코드를 갈아엎었을 것이다.

"전파 차단 아닐까"라는 가설을 명령으로 읽었다면 존재하지 않는 원인을 수정했을 것이다.

### 둘째, 명시 요구와 암묵 요구 분리

"카테고리 추가 시 수정할 곳이 많다"는 명시 요구다.

그 뒤에는 "앞으로 카테고리가 늘어난다"는 암묵 전제가 있다.

따라서 해법은 "지금 3개를 정리"가 아니라 "N번째 추가 비용을 1로 만드는 구조"여야 한다.

### 셋째, 완료 조건 정의

시작 전에 무엇이 확인되면 끝인지 정한다.

- SEO 작업: 빌드 통과가 아니라 실제 HTML의 title/canonical 확인까지
- 드래그 버그: 코드가 그럴듯해지는 것이 아니라 재현되던 조작이 픽셀 단위로 성공하는 것까지

완료 조건을 느슨하게 잡으면 검증도 느슨해진다.

## 2. 애매함 처리 - 모든 애매함이 질문거리는 아니다

애매함은 세 부류로 나눈다.

### A. 사실 확인으로 해소되는 애매함

스스로 해소한다.

예시는 다음과 같다.

- "ui 프로젝트처럼"은 `packages/ui`의 실제 파일 배치를 읽으면 된다.
- 메뉴 훅 위치는 `usePinItemMenu` 소스를 읽어 `PinProvider` 의존을 확인하면 된다.

코드, 문서, git 이력에서 확인 가능한 것을 사용자에게 묻지 않는다.

### B. 합리적 기본값이 있는 애매함

결정하고, 결정했음을 드러낸다.

예시는 다음과 같다.

- 도메인이 미정이면 원본의 `seojaewan.com`을 기본값으로 하되 env override를 가능하게 한다.
- 문서에 없던 2층 구조도 컨텍스트 의존이라는 근거가 있으면 진행하고 문서에 역반영한다.

핵심은 몰래 결정하지 않는 것이다.

### C. 사용자만 답할 수 있는 애매함

멈추고 묻거나, 보고하고 기다린다.

되돌리기 어렵거나 취향/전략이 갈리는 문제는 agent가 결정하지 않는다.

예시는 다음과 같다.

- `page.test.tsx`가 반복 삭제될 때, 처음에는 사고로 판단해 복원했지만 세 번째 삭제에서는 의도로 보고 멈췄다.
- Search Console verification 값은 사용자의 속성에 묶인 값이므로 임의로 넣지 않았다.

## 3. 현재 상태 파악 - 코드보다 기준을 먼저 찾는다

구현 전 정적 분석에서 찾는 것은 세 가지다.

### 기준

무엇과 비교하는지 찾는다.

원본 blog와 `seojaewan.com`이 UX/기능 기준이라면 해당 라우트, sitemap, robots, metadata를 읽는다.

### 컨벤션

어떤 모양이어야 하는지 찾는다.

- lint 설정
- 기존 파일 배치
- import 스타일

lint가 알려주기 전에 먼저 맞추면 재작업이 줄어든다.

### 제약

무엇이 설계를 강제하는지 찾는다.

예를 들어 sync 스크립트가 `tsx`로 실행되어 `@/` alias를 못 쓰면, config 파일은 alias-free여야 한다.

소비자, 스크립트, CI 워크플로까지 먼저 훑는다.

## 4. 계획 - 분해 단위는 되돌아갈 수 있는 지점

작업 분해 기준은 두 가지다.

- 각 단계가 끝날 때 시스템이 검증 가능한 상태인가
- 앞 단계가 뒤 단계의 전제인가

리팩토링은 다음처럼 나눌 수 있다.

```text
기계적 rename
→ 폴더화
→ 로직 분해
→ 라우트
```

어느 단계에서 문제가 나도 그 단계만 의심할 수 있어야 한다.

규모가 크거나 판단이 개입되는 작업은 계획을 문서로 먼저 고정한다.

반대로 자명한 소규모 작업은 문서 없이 바로 간다.

문서화 자체도 비용이기 때문이다.

## 5. 실행 - 코드를 고칠 때의 규칙

### 원인 층위에서 최소로 수정한다

증상을 덮는 코드를 추가하지 않는다.

예를 들어 스크롤 되돌리기나 세션 재시작 로직보다 원인을 제거한다.

- `overflow: clip`
- cleanup 삭제

지우는 수정은 지워도 안전하다는 논증을 완성한 뒤에만 한다.

### 리팩토링과 동작 변경을 섞지 않는다

파일 이동 단계에서는 로직을 바꾸지 않는다.

섞이면 회귀의 원인이 이동인지 변경인지 구분할 수 없다.

### 주석은 왜만 남긴다

코드가 말할 수 없는 이유만 주석으로 남긴다.

- 왜 cleanup이 없는지
- 왜 비율이 아니라 픽셀인지

주석의 역할은 미래의 누군가가 반직관적인 코드를 되돌려 재발시키는 것을 막는 것이다.

### 도구 선택 기준은 오류 확률이다

- 동일 패턴 치환은 손 편집보다 `sed`와 사후 grep
- 정렬은 사람보다 `eslint --fix`
- 이동은 `mv`보다 `git mv`

## 6. 막혔을 때 - 가설-측정 루프

예상과 다른 버그나 이상 동작을 만나면 모드가 바뀐다.

### 규칙 1. 재현 없이는 수정 없다

재현이 안 되는 버그를 고치는 것은 어둠 속 사격이다.

재현 환경이 없으면 만드는 것 자체가 첫 작업이다.

### 규칙 2. 가설은 복수로 세우고 판별 실험을 붙인다

좋은 실험은 결과가 가설을 갈라놓는다.

- 리마운트라면 DOM 마커가 사라져야 한다.
- `pointercancel`이라면 리스너가 울려야 한다.

울리지 않으면 그 가설은 죽는다.

### 규칙 3. 실험은 싼 것부터

비용이 낮은 순서로 올라간다.

```text
grep
→ 스크립트 계측
→ 소스 probe와 재빌드
```

소스 계측은 외부 관찰로 판별이 안 될 때만 사용하고, 확정 즉시 제거한다.

### 규칙 4. 측정 도구 자체를 의심한다

테스트 실패가 곧 버그 재현은 아니다.

관측 장치가 틀렸을 수 있다.

예를 들어 `elementsFromPoint`로 포인터 지점의 요소 스택을 확인한다.

### 규칙 5. 비결정적 증상은 재현율을 측정한다

"가끔 된다"는 보고로는 부족하다.

반복 실행으로 숫자를 만든다.

예시는 다음과 같다.

- 수정 전: 4/6 실패
- 수정 후: 0/6 실패

숫자가 있어야 고쳐졌다고 말할 수 있다.

### 규칙 6. 규명은 수정의 정당성에 필요한 만큼만 한다

모든 내부 메커니즘을 끝까지 쫓지 않는다.

`overflow: clip`이 메커니즘과 무관하게 스크롤을 차단하면 브라우저 내부 스크롤 메커니즘은 끝까지 규명하지 않아도 된다.

반대로 누가 세션을 죽이는지는 스택까지 쫓아야 한다.

무엇을 지워야 할지 결정하려면 원인 주체가 필요하기 때문이다.

## 7. 검증 - 층위와 충분함의 판단

검증은 네 층이다.

1. typecheck/lint: 기계적 오류
2. test/build: 계약
3. 실동작: 서버를 띄우고 실제 응답/조작 확인
4. 사용자 환경 재현: dev/prod, 실제 제스처, 겹친 창 좌표

이번 세션의 교훈은 3층까지 통과한 버그가 존재했고, 4층에서 prod만 확인해 dev 버그를 놓쳤다는 것이다.

따라서 검증 환경은 내가 재현한 환경이 아니라 사용자가 실행하는 모든 모드여야 한다.

충분성 판단 기준은 틀렸을 때의 비용이다.

검증이 불충분했음이 드러나면 검증 체계도 수정 대상이다.

## 8. 보고와 잔류물 - 끝났다고 말하는 방식

보고는 다음 순서가 좋다.

1. 결론
2. 근거
3. 상세

숨기지 말아야 할 것은 다음과 같다.

- 내가 내린 재량 결정
- 내가 틀렸던 것
- 내 권한 밖의 이상 징후

잔류물은 다시 필요해질 위치에 남긴다.

| 잔류물 | 위치 |
| --- | --- |
| 결정의 이유 | 문서 |
| 반직관적 코드의 방어 | 코드 주석 |
| 프로세스 교훈 | 메모리 |
| 일회용 계측 | scratchpad |
| 회귀 가치가 있는 계측 | 공식 테스트 또는 검증 스크립트 |

## 한 문장 요약

모든 명제를 확인된 사실과 추측으로 분류하고, 행동은 사실 위에서만 하며, 추측은 가장 싼 실험으로 사실로 바꾸고, 해소 주체가 내가 아닌 애매함은 투명하게 사용자에게 올린다.

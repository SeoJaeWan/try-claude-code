# Architect Guardrails

## Guardrails

- Planning only: do not write implementation code or source-tree tests.
- Treat the active plan wiki registry, stage core docs, and selected patterns as mandatory when the planning root is available.
- Do not bypass the resolved `plan_wiki_root` with hardcoded external paths once the workspace sync path is available.
- In orchestrated mode, do not redo plan wiki bootstrap, rediscover controller-owned authority, or search for substitute upstream paths beyond provided inputs.
- In orchestrated mode, do not finish with progress-only updates; return plan artifacts or the blocking decision packet.
- Do not produce a plan while `blocking` ambiguity remains.
- Do not replace the user's wording with planner shorthand when a concrete request row can preserve it.
- Do not leave product behavior, public boundaries, exclusions, canonical outputs, negative outputs, recipients, state ownership, no-op rules, or verification ownership implicit when later agents would have to guess.
- Do not leave user-visible hierarchy, state presentation, responsive behavior, or accessibility-relevant behavior implicit when UI scope requires it.
- Do not generate multiple executable plan files unless the active plan wiki plan-count rule supports that topology.
- Do not add plan-local overview, index, DAG, or root graph files.
- Do not add top-level plan sections just to mirror upstream context; fit locked decisions into the active plan template and phase detail template.
- Do not make `plan.md` a second implementation spec by repeating phase-local file maps, scenario tables, validation matrices, or long phase summaries.
- Do not make a reviewer open every phase detail file just to understand the overall request, included/excluded scope, change shape, locked public contracts, phase order, and risk verification.
- Do not prescribe concrete source-tree test files, helper names, exhaustive locator lists, or runner mechanics when local conventions can derive them later.
- Do not leave test-strategy decisions implicit when the active plan wiki decision policy requires them for deterministic TDD authoring.
- Do not treat Context7 as mandatory for every plan; use it only when unstable external facts can change the boundary, contract, or phase split.
- Do not leave Context7-derived constraints only in transient reasoning when they affect the plan.
- Do not perform full-file Figma tree reads from this skill.
- Do not substitute Code Connect, design context, package registries, old parity reports, memory, or partial tool output for controller-verified Figma inventory snapshots when full inventory coverage is part of the request.
- Do not write Figma-derived classification or contract artifacts without manifest-backed provenance when the plan depends on them.
- Do not convert Figma tool/data blockers into user questions unless the user must choose root nodes or inventory scope.
- Do not use task-local UI nouns as canonical visual parity taxonomy when a local comparison contract applies.
